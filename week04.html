이 문서는 1주차부터 이미 쓰고 있었습니다. 오늘은 새로 쓰는 것이 아니라 남은 빈칸을 채우고 앞뒤를 맞추는 주입니다. agent-design.md는 이 수업의 축입니다. 3주차 설계지침을 받아 5주차 코드로 넘기는 접점이고, 동시에 연구 산출물이며, Claude Code와 Codex에 그대로 넣는 입력 문서이기도 합니다. 세 가지 역할을 한 문서가 합니다.

학습목표

  1. 설계지침을 에이전트의 역할·기능·상호작용 흐름으로 옮길 수 있다.
  2. 스캐폴딩 수위와 페이딩 규칙, 금지 정책을 실행 가능한 문장으로 명세할 수 있다.
  3. 평가 지표와 로그 항목을 명세서 안에 미리 설계할 수 있다.
  4. 구현에 쓸 기술 스택과 모델 설정을 계획으로 기록하고, 그것이 명세의 어느 항목을 제약하는지 판단할 수 있다.
질문 1

명세서는 왜 코드보다 먼저인가?

AI 코딩 도구를 쓰면 "일단 만들어 보고 고치자"가 매우 쉬워집니다. 그리고 그것이 이 수업에서 가장 흔한 실패 경로입니다. 프로토타입은 빨리 나오는데, 6주차에 "이 기능의 근거가 무엇입니까"라는 질문에 답하지 못합니다.

명세서의 역할없으면
연구 산출물 설계 과정이 기록되지 않아 개발 연구가 아니라 개발 후기가 된다
구현 입력 대화할 때마다 다른 요구를 주게 되고, 에이전트 행동이 일관되지 않는다
평가 기준 6·7주차에 무엇을 평가할지 그때 가서 정하게 되고, 결과가 설계와 연결되지 않는다
명세서를 쓰는 일은 구현 전에 설계 결정을 모두 내리는 일이 아니다. 어떤 결정을 내렸고 왜 내렸는지 기록하는 일이다. 구현하면서 결정이 바뀌면 명세서를 고치면 된다 — 고친 이력이 곧 연구 자료다.

agent-design.md를 GitHub 저장소에 두고 커밋 이력을 남기세요. 6주차 전문가 타당화 후 무엇을 왜 고쳤는지가 자동으로 기록됩니다. 8주차 보고서의 "개선 이력" 절을 커밋 로그로 쓸 수 있습니다.

자기점검 지금 만들려는 기능 중 3주차 지침 ID를 붙일 수 없는 것이 있는가?
질문 2

이 에이전트는 누구인가?

명세서의 첫 절은 정체성입니다. 이름과 말투가 아니라 무엇을 하는 존재이고 무엇을 하지 않는 존재인지를 정합니다.

항목정하는 것예
역할1주차 여섯 역할 중 무엇인가코치 (주) + 평가자 (보조)
대상누구와 대화하는가중2 학습자. 교사는 설정 화면만 사용
범위어떤 과제에 한정되는가주장하는 글의 개요 작성 단계에 한정
경계범위 밖 요청에 무엇을 하는가한 번 안내하고 원래 과제로 돌린다
말투어떤 어조로 말하는가존댓말, 3문장 이내, 감탄사 없음
호칭자신과 학습자를 어떻게 부르는가"저" / "○○님". 자신을 교사라 칭하지 않음

함정 · 페르소나 과잉

"친근한 20대 대학생 언니 같은 AI 튜터"처럼 인격을 정교하게 만들수록 좋다고 생각하기 쉽습니다. 그러나 페르소나가 두꺼워지면 교육적 판단이 캐릭터 연기에 밀립니다. 학습자가 틀렸을 때 캐릭터를 유지하려고 "괜찮아요, 잘하고 있어요"를 하게 됩니다. 페르소나는 얇게, 행동 규칙은 두껍게 쓰세요.

지금 해볼 것 · 15분

위 여섯 항목을 채우고, 경계 항목을 특히 구체적으로 쓰세요. "수학 문제 풀어줘", "숙제 대신 해줘", "너 누구야?", "오늘 기분 안 좋아" 네 가지 요청에 각각 무엇이라 답할지 실제 문장으로 적어 보세요.

질문 3

무엇을 할 수 있어야 하는가?

여기서 3주차 추적표의 마지막 열을 채웁니다. 지침 하나가 기능 하나 이상으로 내려갑니다. 반대로, 어떤 지침에서도 나오지 않은 기능은 넣지 않습니다.

기능 ID기능근거 지침우선순위
F1학습자의 근거 제출을 감지하고 평가 기준 한 항목을 제시G1-1필수
F2시도 횟수를 세어 힌트 수위를 결정G2-1, G2-2필수
F3해답 요구를 감지해 거절하고 더 작은 질문으로 전환G2-3필수
F4세션 종료 시 학습자에게 성찰 질문 제시G4-1권장
F5교사가 평가 기준을 수정할 수 있는 설정G5-2선택

우선순위는 세 칸으로만

필수 — 이것이 없으면 원리가 구현되지 않는다. 5주차에 반드시 만든다.
권장 — 있으면 좋다. 시간이 남으면 만든다.
선택 — 이번 학기에는 명세만 하고 만들지 않는다. 보고서에 "향후 과제"로 적는다.

8주 과정에서 필수 기능은 4–6개가 현실적입니다. 그보다 많으면 5주차에 아무것도 완성하지 못합니다.

지금 해볼 것 · 20분

기능 표를 채우고, 필수로 표시한 것이 6개를 넘으면 강제로 줄이세요. 줄이는 기준은 "이 기능이 없으면 어떤 원리가 검증 불가능해지는가"입니다. 검증에 꼭 필요한 것만 필수입니다.

agent-design.md 2절 기능 표. 동시에 3주차 추적표의 비어 있던 「기능」 열을 채우세요. 양쪽 ID가 맞아야 합니다.

자기점검 근거 지침 칸이 빈 기능이 있는가? 있으면 지우거나, 지침을 거슬러 올라가 근거를 찾는다.
질문 4

학습자와 어떻게 주고받는가?

기능 목록만으로는 에이전트를 만들 수 없습니다. 대화가 어떻게 흘러가는지를 써야 합니다. 세 가지를 명세합니다.

1 · 흐름

단계에이전트가 하는 일다음으로 가는 조건
진입과제와 목표를 확인시키고 학습자의 계획을 묻는다학습자가 시작 의사를 밝힘
산출학습자가 초안을 쓰도록 두고 개입하지 않는다학습자가 초안을 제출
점검기준 한 항목을 제시하고 스스로 판단하게 한다학습자가 판단을 말함
조정판단에 따라 힌트 수위를 조절한다기준을 충족하거나 최대 턴 도달
종료무엇이 달라졌는지 성찰을 요구한다—

2 · 상태

에이전트가 턴을 넘기며 들고 가야 할 값입니다. 5주차에 이것이 그대로 코드가 됩니다.

상태 스키마 
session:
  phase:          진입 | 산출 | 점검 | 조정 | 종료
  turn_count:     정수
  attempt_count:  학습자가 스스로 시도한 횟수
  hint_level:     L0 | L1 | L2 | L3
  criteria_shown: [제시한 기준 항목 목록]
  criteria_met:   [학습자가 충족한 기준 항목 목록]
  answer_requests: 해답을 직접 요구한 횟수
  off_topic_count: 범위 밖 요청 횟수

learner:
  draft:          현재 초안 텍스트
  self_judgments: [학습자가 스스로 내린 판단 기록]

3 · 예시 대화

명세서에 실제로 오갈 대화 한 편을 붙이세요. 표보다 이것이 훨씬 많은 것을 결정합니다. 특히 잘 안 풀리는 경우를 반드시 쓰세요.

써야 할 예시 대화 네 편

  • 정상 경로 — 학습자가 협조적이고 과제가 잘 풀린다
  • 막히는 경로 — 학습자가 세 번 시도해도 못 한다
  • 회피 경로 — 학습자가 답을 달라고 조른다
  • 이탈 경로 — 학습자가 딴 얘기를 하거나 장난친다

네 편이면 충분합니다. 5주차에 이 네 편이 그대로 테스트 시나리오가 됩니다.

지금 해볼 것 · 30분 · 짝 활동

한 사람은 학습자, 한 사람은 에이전트가 되어 손으로 대화를 10턴 주고받으세요. 에이전트 역할을 맡은 사람은 자기 지침만 보고 응답해야 합니다. 지침으로 다음 말을 정할 수 없는 순간이 반드시 옵니다 — 그 순간이 명세서에 빠진 부분입니다. 표시해 두고 채우세요.

agent-design.md 3.1 흐름 표와 3.3.1 정상 경로. 지침으로 다음 말을 정할 수 없었던 순간은 그 자리에 주석으로 남기고, 이번 주 안에 채우세요.

자기점검 예시 대화 네 편 중 "막히는 경로"와 "회피 경로"를 썼는가? 정상 경로만 쓴 명세서는 5주차에 무너진다.
질문 5

언제 도와주고 언제 참는가?

교육용 에이전트의 핵심이자, 일반 챗봇과 갈라지는 지점입니다. 참는 규칙을 명시하지 않으면 LLM은 반드시 답을 줍니다. 도움을 주는 조건보다 참는 조건을 더 자세히 쓰세요.

스캐폴딩 수위

수위에이전트의 행동예
L0개입하지 않는다"천천히 해 보세요."
L1방향만 가리킨다"방금 쓴 문장이 주장인가요, 근거인가요?"
L2부분 예시를 준다"다른 학생은 이런 근거를 들었어요. (예시 하나)"
L3절차를 안내한다"근거를 찾을 때는 먼저 ○○을 확인하고, 그다음 ○○을 해 보세요."

올리는 규칙과 내리는 규칙

조건조치
학습자가 시도했으나 같은 오류를 반복수위를 한 단계만 올린다
학습자가 "모르겠다"만 반복하고 시도가 없음수위를 올리지 않고 과제를 더 작게 쪼갠다
학습자가 스스로 기준을 충족수위를 L0으로 되돌린다 (페이딩)
최대 턴(예: 12턴) 도달L3까지 제공하고 교사 개입을 안내한다

페이딩을 잊지 마라

대부분의 학생 프로토타입은 도움을 올리기만 합니다. 한 번 L3까지 가면 끝까지 L3로 답합니다. 그러면 학습자는 나머지 시간 동안 아무것도 하지 않게 됩니다. 내리는 조건을 반드시 쓰세요. 이것이 인지적 도제의 페이딩이고, 6주차 전문가가 가장 먼저 확인하는 항목입니다.

피드백의 형식

유형쓸 때문장 형식
확인학습자의 판단이 맞을 때무엇이 왜 맞는지 기준 항목으로
되묻기판단이 틀렸을 때 (1차)정정하지 않고 근거를 묻는다
대조판단이 틀렸을 때 (2차)기준과 학습자의 글을 나란히 보여준다
정정2차에도 못 잡을 때무엇이 왜 다른지 설명하고 다시 해보게 한다

자기점검 내 명세서에 도움을 줄이는 조건이 적혀 있는가?
질문 6

무엇을 하면 안 되는가?

금지 정책은 "하지 마라"로 끝나면 작동하지 않습니다. LLM에게는 대신 무엇을 할지를 함께 줘야 합니다.

금지대신 할 일
정답 유출 완성된 답·모범 답안을 제시하지 않는다 → 기준 한 항목을 제시하고 스스로 대조하게 한다
범위 이탈 다른 과목·잡담에 응하지 않는다 → 한 번 안내하고 원래 과제의 마지막 지점으로 돌린다
개인정보 수집 실명·학교·연락처를 묻지 않는다 → 이미 입력되면 저장하지 않고 안내한다
불확실한 사실 단정 모르는 것을 지어내지 않는다 → "확인이 필요합니다"라고 말하고 확인 방법을 안내한다
평가·낙인 학습자의 능력을 규정하지 않는다("소질이 없네요") → 행동과 산출물에 대해서만 말한다
정서적 위기 방치 자해·괴롭힘 등 신호를 무시하지 않는다 → 대화를 멈추고 교사·상담 연결을 안내한다

연구윤리 · 학습자 데이터

7주차 사용성 평가에서 실제 학습자의 대화 로그를 수집하게 됩니다. 명세서에 지금 정해 두세요.

  • 무엇을 로그로 남기는가 (턴 내용 / 상태값 / 시각)
  • 개인 식별 정보를 어떻게 제거하는가
  • 어디에 보관하고 언제 삭제하는가
  • 학습자에게 로그 수집을 어떻게 고지하는가

먼저 · 기술 스택을 계획으로 적는다

명세서 7절은 무엇으로 만들 것인가입니다. 코드는 다음 주에 쓰지만, 스택은 지금 정해야 합니다. 스택이 명세의 일부 항목을 가능하게도, 불가능하게도 만들기 때문입니다.

층정하는 것이 결정이 좌우하는 것
구현 경로 A 설정형 / B 앱형 / C 직접 구현 (5주차에서 설명) 아래 전부
프론트엔드 학습자가 보는 화면 — 대화창, 입력란, 상태 표시 7주차 참여자가 설명 없이 쓸 수 있는가
백엔드 요청을 받아 모델에 넘기고 기록을 남기는 쪽 로그가 자동으로 남는가
AI 모델·API 어떤 모델을 어떤 방식으로 부르는가 응답의 성격, 비용, 재현성
데이터 저장 로그를 어디에 어떤 형식으로 남기는가 7주차에 분석할 자료가 존재하는가
배포 · 접속 남이 어떻게 열어 보는가 6주차 전문가 평가가 성립하는가
개발 도구 Claude Code / Codex 5주차 작업 속도

함정 · 내 노트북에서만 도는 프로토타입

가장 흔한 사고입니다. 5주차에 앱을 잘 만들었는데 내 노트북에서만 돕니다. 그러면 6주차에 전문가에게 링크를 줄 수 없고, 7주차에 참여자를 앉힐 수 없습니다. 두 주가 통째로 막힙니다.

그래서 「배포 · 접속」 칸을 지금 채우세요. 셋 중 하나면 됩니다 — ① 공유 링크가 나오는 곳에 올린다 ② 전문가에게는 링크, 참여자는 대면으로 내 노트북에서 진행한다 ③ 설정형(경로 A)의 공유 기능을 쓴다. ②를 택하면 전문가 평가를 화면 공유로 대신할 수 있는지 미리 확인해 두세요.

모델 설정을 기록해야 하는 이유

LLM은 같은 입력에도 매번 다르게 답합니다. 그래서 7주차에 "해답 요구 23회 중 21회 거절(91%)" 같은 숫자를 내놓아도, 무엇을 고정한 상태에서 잰 것인지 적혀 있지 않으면 해석할 수 없습니다.

명세서 7.1에 모델명·버전·설정값·최대 턴 수를 적고, 바뀔 때마다 갱신하세요. 이 표가 그대로 보고서 방법 절이 됩니다. 8주차 질의응답에서 "모델이 바뀌면 결과가 달라지지 않나요"라는 질문을 반드시 받는데, 이 기록이 있으면 답할 수 있습니다.
